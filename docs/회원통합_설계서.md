## 2. 지금 당장 고쳐야 할 보안 문제 (통합보다 먼저)

1. **K-Market DB 권한 규칙이 전부 열려 있음** (`supabase_schema.sql`)
   - `kmarket_sms_logs`: `FOR ALL USING (true)` → 누구나 **다른 사람의 SMS 인증번호**를 읽을 수 있음
   - `kmarket_tax_refund_leads`: 같은 규칙 → 누구나 **외국인등록번호·연락처**를 읽고 수정 가능. 코드(`KMarketTaxModal.tsx`)도 브라우저에서 `arc_number`를 그대로 insert함
   - `kmarket_user_profiles`: 전체 공개 → 전화번호, 등록번호 해시, 신분증 이미지 경로 노출
   - anon 키는 브라우저에 공개되는 값이라, 화면을 거치지 않고 REST 주소를 직접 호출해도 똑같이 읽힙니다.
2. **K-Market ID가 위조 가능**: 서버가 확인하지 않는 `user-<시각>` 값을 신뢰하므로 다른 사람인 척 거래·신고·차단을 할 수 있습니다.
3. **easy-tax 관리자 로그인**: `NEXT_PUBLIC_ADMIN_ID/PASSWORD`(브라우저에 포함됨) + 코드에 적힌 기본 아이디·비밀번호. 비밀번호를 즉시 바꾸고 서버 검사로 교체해야 합니다.
4. **암호화 키 기본값이 소스에 있음** (`automated-refund-estimate.ts`의 `ENCRYPTION_KEY` fallback). 키를 교체하고 기본값을 없애야 합니다.
5. **easy-tax 쪽 RLS는 확인 불가**: `tax_applications` 정의가 저장소에 없고, 브라우저(anon) 클라이언트가 이 테이블을 수정·삭제하는 코드가 있습니다. 대시보드에서 실제 정책을 확인해야 합니다. 상담 테이블(`chat_messages`)은 anon SELECT가 `true`입니다.
6. **개인정보가 서버 로그에 남음**: 이 프로젝트의 `api/apply`, `api/inquiry`, `api/partnership`은 신청자 정보를 `console.log`로 남깁니다. 저장소를 붙일 때 같이 제거합니다.

처리 순서와 SQL은 `phase0_security_patch.sql`에 있습니다. **앱 코드를 서버 API 경유로 바꾼 뒤에 정책을 지워야** 화면이 멈추지 않습니다.

## 2-1. 확정된 결정 (2026-11-06)

| 항목 | 결정 |
|---|---|
| 고객 경험 | **회원가입 화면 없음.** 처음 한 번 신분증 촬영(OCR) + 휴대폰 문자 인증 → 세 앱 어디서든 이용. 다음부터는 문자 인증만으로 저장된 정보를 불러옴 |
| 정보 불러오기 | 휴대폰 문자 인증만으로 가능 (등록번호 뒷자리·생년월일 같은 2차 확인은 두지 않음) |
| 신분증 사진 | **저장하지 않음.** OCR 결과만 암호화 저장, 요청이 끝나면 사진은 즉시 폐기 |
| 도메인 | 새 도메인을 만들어 서브도메인으로 운영 (`tax.` / `market.` / `telecom.`) → 로그인 쿠키를 `.도메인`으로 공유하면 앱 이동 시 재인증 불필요 |

**받아들인 위험 (참고)**: 문자 인증만으로 정보를 열기 때문에 ① 인증 문자가 진짜여야 하고(현재 K-Market은 인증번호가 화면으로 내려옴 → 0단계에서 먼저 수정), ② 해지된 번호를 다른 사람이 재할당받은 경우 이전 사람의 정보가 열릴 수 있습니다. 완화책으로 화면에는 등록번호를 항상 가려서(`•••••• 1234`) 보여주고, 전체 번호는 서버에서만 사용하며, 로그인 유지 기간을 짧게(예: 30일) 둡니다.

## 3. 목표 구조

```
            Supabase Auth (auth.users)  ← 회원의 유일한 기준
                       │
              member_profiles (전화번호, 이름, 국적, 언어)
              app_memberships (ktrs / kmarket / ktelecom)
                       │
   ┌───────────────────┼────────────────────┐
   ▼                   ▼                    ▼
 세무 앱           K-Market 앱         K-Telecom 앱
 (신분증 필요)     (인증 여부만)       (신분증 필요)
   └─────── 서버(서비스 키)에서만 identity_documents 접근 ───────┘
```

- **신분증은 한 번만**: `identity_documents`에 암호화 저장. 세 앱은 서버를 통해서만 읽고, 읽을 때마다 `identity_access_log`에 남깁니다.
- **앱별 노출 범위**
  - K-Market: `member_public_v` 뷰(이름·국적·인증 여부). 등록번호는 절대 접근 불가
  - 세무·통신: 서버에서 필요한 항목만 복호화. 화면에는 마스킹(`•••••• 1234`)으로 보여줌
- **브라우저는 신분증 테이블에 직접 접근하지 않습니다**(정책 없음 = 거부).

## 4. 로그인 방식

Supabase Auth의 기본 휴대폰 인증은 Aligo를 지원하지 않으므로, 이미 쓰는 Aligo OTP를 그대로 쓰고 **세션만 Supabase Auth로 만듭니다.**

1. 사용자가 전화번호 입력 → 서버가 Aligo로 OTP 발송(해시·만료·시도 횟수 제한, 지금 easy-tax 방식 재사용)
2. OTP 확인 성공 → 서버가 `auth.admin.createUser`(없을 때만)로 계정 생성. 전화번호만 있는 사용자를 위해 내부용 가짜 이메일(`p<번호>@phone.invalid`)을 쓰고 전화번호는 `member_profiles.phone_e164`에 저장
3. 서버가 `auth.admin.generateLink({ type: 'magiclink' })`로 1회용 토큰을 만들고 `verifyOtp`로 **정상 Supabase 세션** 발급
4. 이후 브라우저의 모든 요청은 `auth.uid()`로 본인 행만 접근

## 5. 앱 사이 이동 (한 번 로그인하면 세 앱 모두)

- **새 도메인 + 서브도메인(확정)**: `tax.도메인`, `market.도메인`, `telecom.도메인`. 세 앱이 같은 Supabase 세션 쿠키를 `.도메인`으로 공유하면(`@supabase/ssr`의 쿠키 `domain` 옵션) 한 번 인증한 고객은 다른 앱에서 다시 인증하지 않습니다.
  - 새 도메인이 열리기 전(`*.vercel.app` 사용 중)에는 아래 1회용 코드 방식이 임시로 필요합니다.
- **도메인이 서로 다른 경우(`*.vercel.app`, 임시)**: `sso_handoff` 테이블의 1회용 코드로 이동
  1. 앱 A 서버가 코드 발급(저장은 해시만, 60초 만료, 1회 사용)
  2. 앱 B로 `?handoff=코드` 이동
  3. 앱 B 서버가 코드를 검증하고 자기 도메인에서 세션 발급
- **금지**: 계획서의 `?user_id=UUID`로 신분증 정보를 자동 채우는 방식. UUID만 알면 남의 정보를 볼 수 있습니다.

## 6. OCR 한 번 저장 → 세 앱에서 사용

```
사진 업로드 ─▶ 서버 API(/api/identity/ocr)
               · 로그인 세션 확인
               · 동의 확인(identity_collect, ocr_overseas_transfer)
               · Gemini OCR (K-Market의 geminiOcrService 재사용)
        ─▶ 결과를 사용자에게 보여주고 확인·수정 (verification = user_confirmed)
        ─▶ 저장: 번호는 AES-256-GCM 암호화 + HMAC 해시 + 마지막 4자리
               · 이미지는 저장하지 않음 (OCR 요청이 끝나면 즉시 폐기)
        ─▶ 세 앱 신청서는 /api/identity/prefill (서버) 로 필요한 항목만 받아 자동 채움
```

- **OCR은 글자 읽기일 뿐 진위확인이 아닙니다.** 통신 개통의 본인확인·신분증 진위확인은 제휴사(아이즈모바일)/통신사 시스템이 합니다. `partner_verified`는 그 결과가 돌아왔을 때만 올립니다.
- 같은 신분증으로 계정이 둘 생기지 않도록 `number_hash` 유일 제약을 둡니다. 충돌하면 계정 병합 절차로 안내합니다.

## 7. 기존 데이터 이관

- K-Market: `kmarket_user_profiles`(전화번호 기준) → `member_profiles`, 옛 ID는 `legacy_user_map`
- 세무: `tax_applications`(전화번호+등록번호 기준) → 같은 사람이면 같은 `user_id`
- 기존 평문 `arc_number`는 이관 중 암호화하고 원본 컬럼은 비우거나 삭제
- 전화번호가 없거나 겹치는 행은 자동 병합하지 않고 목록으로 뽑아 사람이 확인

## 8. 법적 확인 사항 (코드로 해결되지 않는 부분)

- 외국인등록번호는 **고유식별정보**: 수집 근거, 별도 동의, 암호화, 접근 통제 필요
- 세무 / 통신 / 중고거래는 목적이 달라 **목적별 동의**(`consents`)를 따로 받아야 합니다.
- Gemini 등 해외 AI에 신분증 이미지를 보내는 것은 **국외 이전 고지·동의**가 필요할 수 있습니다.
- 개인정보 처리방침 문구와 보관 기간은 법무 검토 후 확정

## 10. Supabase 명령어

아래는 **DB와 환경에 영향을 주므로 스테이징에서 먼저** 실행하세요. 프로젝트 ref는 `ilvxvohksgwdiyvpkwag`(주소에 들어 있는 값, 비밀 아님)입니다.

### 방법 A. 대시보드 (가장 간단)
1. Supabase 대시보드 → 해당 프로젝트 → **SQL Editor** → New query
2. `docs/member_integration.sql` 내용을 붙여넣고 **Run**
3. 확인: Table Editor에서 `member_profiles`, `identity_documents` 등이 생겼는지 확인

### 방법 B. CLI
```powershell
npx supabase login
```
```powershell
npx supabase link --project-ref ilvxvohksgwdiyvpkwag
```
적용 전 백업(필수):
```powershell
npx supabase db dump -f backup_before_member_integration.sql
```
마이그레이션 파일로 만들어 적용:
```powershell
npx supabase migration new member_integration
```
생성된 `supabase/migrations/…_member_integration.sql`에 `member_integration.sql` 내용을 붙여넣은 뒤:
```powershell
npx supabase db push
```

### 현재 권한 규칙 점검 (SQL Editor에서 실행, 읽기 전용)
```sql
select schemaname, tablename, policyname, roles, cmd, qual
from pg_policies where schemaname = 'public' order by tablename, policyname;
```

### 암호화 키 만들기 (신분증 번호용 32바이트)
```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```
같은 방법으로 해시용 비밀값(`IDENTITY_HASH_PEPPER`)도 따로 만듭니다. 두 값은 **서버 환경변수에만** 넣고 `NEXT_PUBLIC_`을 붙이지 않습니다.
```powershell
npx vercel env add IDENTITY_ENC_KEY production
```
```powershell
npx vercel env add IDENTITY_HASH_PEPPER production
```
> 키를 잃어버리면 암호화된 번호를 복구할 수 없으니 안전한 곳에 따로 백업하세요.
